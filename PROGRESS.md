Both hosts save after every login attempt and load at start; `--reset-login-limits` deletes the file. Bans now last until that reset instead of until restart. A wall clock that went backwards cannot push failures into the future, and a restored global lockout is capped at its configured length.
  - **Hidden password prompts**: `spike-viewer` and `p2p-connect` read the password with `rpassword` (no echo) on a console; when stdin is not a terminal they read one line from it, so scripts can pipe the password.

## Known issues

- UI refinement: the streaming toolbar, fullscreen, the actions menu and the password dialog were built and unit-tested but not yet seen with a live session; AccessKit in the viewer is untested with a screen reader; the Linux build with the new `accesskit` feature was not rebuilt in the Debian image yet (`packaging/linux/build.sh check`). The fonts are still egui's defaults (Ubuntu-Light has no bold, so hierarchy comes from size and colour); bundling Inter was left for a decision (download and licence file).
- Linux: viewer only. No screen capture (X11/PipeWire) or input injection (uinput/libei) backend, so nobody can connect to a Linux machine; no keyboard grab, so system keys (Super, Alt+Tab, Alt+F4, anything the desktop environment binds) stay local. Not yet checked by hand on a real Debian desktop (Wayland and X11), nor with a real Windows host from Linux.
- Linux build: `.cargo/config.toml`'s libvpx paths are Windows-only; Linux builds need the exported `VPX_*` variables (`packaging/linux/build.sh env`). A checkout shared with Windows must install the Linux libvpx outside `./vcpkg_installed` (`VCPKG_INSTALL_ROOT`), because a manifest-mode install removes other triplets from its root. The tarball has no desktop entry or icon yet, and no `.deb`.
- Desktop app: the viewer registers with the ID server under its own device key and ID (in `data\client`), separate from the host's, so one machine has two IDs (only the host's is shown). Entering the viewer's own ID gets a clear message.
- Desktop app: no tray icon; closing the main window stops a host it started (sessions end). A host started otherwise (`kanodesk --server`) keeps running. `hide_cm`, the direct-access listener, fps and bitrate still need a host restart; the rest of Settings applies live.
- Desktop app: no remembered passwords, address book, favourites, LAN discovery or online dots in Recent sessions yet; no keyboard-mode or relative-mouse buttons in the toolbar (shortcuts only); no quality monitor beyond fps. Quality presets are per display, shared by every viewer of it (latest wins).
- Desktop app: UPnP mapping is not used by the host's presence (the CLI `p2p-host` has it); ID-server settings support one server, no fallback list.
- Host process runs as the logged-in user; prompt 11's service runs it as SYSTEM in the user's session and starts the CM with the user's token. The pipe check (same Windows session) already fits that split.
- The CM shows a client's self-reported host name and user; only the device key (Noise) and address are verified. There is no trusted-device list or 2FA yet.
- One shared encoder per display means every viewer of a display gets the same bitrate and frame rate (11 §2's trade-off); per-viewer quality comes with QoS.
- `hide_cm` is honoured only in `password` mode; there is no tray icon or "stop service" yet.
- No auto-disconnect on inactivity, no audit log, and the CM has no chat or file log (11 §3.4, §4.1).

- Input: Ctrl+Alt+Del and Win+L are handled by Windows below any hook and stay local; Ctrl+Alt+End sends Ctrl+Alt+Del instead (performed once the service exists). In Translate mode the keyboard grab is off, so system keys stay local there.
- Input: `SendInput` cannot reach the secure desktop (Ctrl+Alt+Del screen, UAC prompts, lock screen) or windows of higher integrity (elevated apps) from a normal user process. That needs the SYSTEM service host of 14.
- Input: lock keys are synchronised as states (the host toggles on the next key), not sent as keys, so a host app that remaps Caps Lock does not see it pressed. IME composition on the viewer is not supported in Translate mode (characters arrive after composition only if winit delivers them as key text). Sleep/Wake/Power consumer keys are deliberately not mapped. Touch/pen are not implemented. The low-level keyboard hook is skipped by Windows if the viewer's window thread stalls for longer than the hook timeout (keys then reach the local system).
- Input: on one machine, streaming the display the viewer window is on makes the pointer chase itself (each injected move changes what is under the pointer). Stream another display. The extra-info marker stops the keyboard feedback loop (verified); for mouse events it relies on winit handling the move inside the window procedure, which was not checked live.
- Input: the spike toggles keyboard and mouse together (Enter in the host console); the protocol and the injector handle them separately.
- Input: a network stall of more than 3 s while keys or buttons are held releases them on the host; modifiers come back on the next key and other keys with the next auto-repeat, but a mouse drag in progress is ended.
- Input: touchpad pixel scroll deltas are sent 1:1 as wheel units, an approximation.

- **libvpx is pinned to 1.13.1** because `env-libvpx-sys` only ships pregenerated bindings up to 1.13.0 and generating them needs libclang. 1.13.1 lacks later fixes, such as CVE-2024-5197 (`vpx_img_alloc`/`vpx_img_wrap` integer overflow; we only wrap images whose size we control). Before phase 1 ships, move to current libvpx with generated bindings (install LLVM, enable `env-libvpx-sys/generate`) or our own bindings.
- The host's pointer appears only after it first moves on the host (DXGI reports the pointer on change); "invert" pointer pixels (I-beam) are drawn black. The pointer position is sent at most once per captured frame (30 Hz by default).
- Rotated displays are not handled: the duplicated image comes back unrotated.
- HDR / 10-bit desktops are not handled: `IDXGIOutput1::DuplicateOutput` gives BGRA8, but `IDXGIOutput5::DuplicateOutput1` would be needed for proper HDR.
- No GDI fallback yet for where DXGI fails (some RDP sessions, Windows 7). The secure desktop needs the service/SYSTEM setup from phase 1 (14).
- Dirty rectangles are not used yet; every changed frame is copied and encoded in full (06 §10 lists dirty-rect skipping as the next optimisation).
- `next_frame` returns `Ok(None)` forever if duplication never becomes possible again (for example a display that stays on the secure desktop); a caller-side timeout and a GDI fallback are needed later.
- Fuzzing is not in CI (it needs nightly). The fuzz body does run in CI on stable through the `decoder_never_panics_on_random_bytes` proptest, but without coverage guidance or ASan. On Windows, `cargo fuzz run` needs the MSVC ASan DLL on `PATH` (see README).
- `Permission`/`Ping`/`ReceiverReport`/input messages are defined but not used yet; their shape may still change before phase 1 ships (protocol is still v1 and unreleased, so changing them now is fine).
- The transport has no test for a stream with the wrong header kind (it needs a raw QUIC stream); the error path is simple but unexercised.
- NAT traversal is only tested on loopback, where black-holed addresses stand in for blocking NATs. No real NAT lab yet (16 §7 suggests netns/Docker with full-cone, restricted, port-restricted and symmetric NATs); the manual two-machine test is the first real check.
- Hole punching is still simple: the controller races handshakes against the host's punch bursts. Port prediction is a fixed window of the next 16 ports, which only helps NATs that allocate sequentially; there is no NAT-PMP/PCP and no TCP fallback; symmetric↔symmetric goes straight to the relay. UPnP is untested against a real router (none on this network).
- Virtual adapters are recognised by name (`nat::VIRTUAL_ADAPTERS`), so an adapter with an unusual name still gets offered, and a VPN adapter's private address can still win a LAN race between peers behind the same public IP. Harmless (the connection works), just not always the best path.
- The relay is single-process, with no clustering, metrics endpoint or abuse reporting. Relay hellos every 10 s handle NAT rebinding, but packets sent between a rebinding and the next hello are lost (QUIC retransmits them).
- Peer TLS accepts any certificate (`InsecureAcceptAny`); peers authenticate with Noise IK bound to the TLS session's channel binding instead, so a TLS man-in-the-middle cannot complete the login.
- Login limits are kept per source IP. Peers that share an IP (a big NAT) share backoffs and bans; bans last until the owner runs the host with `--reset-login-limits`. The state file is not integrity-protected (anyone who can write the host's data dir can clear it, but could also do much worse).
- A temporary password admits one login, so a viewer that disconnects needs the new password the host prints (or the permanent password). Approving each login on the host (04) comes with the real host UI.
- `--password` on the command line is visible to other local users (process list) and in shell history; the hidden prompt avoids that. The real UI will have a proper password field.
- The ID server only pushes the relay list, not alternative ID-server addresses.
- ID server: the TLS certificate is a throwaway self-signed one; clients authenticate the server only through the signed `ServerHello` bound to the TLS session. That is sound, but means a client must use an endpoint that accepts any certificate for the ID server.
- ID server: key-loss recovery is manual (`remove`, then re-register); there is no self-service flow, by design, since anyone could claim to have lost a key.
- ID server: outside `--trusted-network`, new-ID creation and unregistered requests are limited per source IP.
- ID server online admin authenticates with the server's own signing key, so it is limited to whoever can read the server's key store (the machine's administrators); there are no separate operator accounts or audit log. `relays` (print the saved list) works only with the server stopped.
- ID server on non-Windows keeps its signing key in a plain owner-only file; use disk encryption or an HSM-backed store for production.
- This machine's Windows Application Control policy blocks some freshly built test executables (os error 4551). It hit the empty test harness of `kanodesk-idserver`'s `main.rs`, which is now `test = false`; if it hits another, rerun or allow the build directory.
- The spike authenticates viewers (Noise IK + SPAKE2) but is still a test tool: one keyboard+mouse permission toggled from its console, no session approval (prompt 9), one viewer at a time. Keep `spike-host` on localhost/LAN tests.
- Video frames are sent **reliably** on the video stream. 16 §4 wants unreliable delivery with keyframe recovery; on a lossy link, reliable delivery adds head-of-line delay. Revisit with QoS.
- The spike latency number relies on both processes reading the same QPC clock, so it only works on one machine, and it stops at the viewer's `present()` call (scan-out not included).
- `spike-host` serves one viewer at a time; a new viewer replaces the current one. DXGI allows one duplication per output per process (a second `DuplicateOutput` fails with `E_INVALIDARG`), so several viewers need one shared capture per display fanned out to per-viewer encoders.
- The viewer's mailbox skips 8–14 frames per session, all during start-up while the window and swapchain are created; none in steady state.
- `spike-host` reports how a viewer left only roughly ("disconnected" for a deliberate close by the viewer, otherwise the I/O error).
- Capture is paced on a fixed 33 ms tick, which adds 0–33 ms of waiting (the "host" stage). Capturing on the desktop's update instead of a tick would cut average latency further.
- The CI workflow has not run yet: there is no GitHub remote. Its first run builds libvpx (~3 min); later runs hit the cache.

| 2026-10-11 | One envelope per stream type (`ControlMessage`, `VideoMessage`, `InputMessage`), each stream opened by a `StreamHeader` | Matches the 16 §4 stream layout; a stream can only carry messages that belong on it |
| 2026-10-11 | Fixed 4-byte big-endian length header, not RustDesk's 1–4 byte varint header (05 §1) | QUIC already frames streams; a fixed header keeps the decoder trivial and easy to fuzz |
| 2026-10-11 | `Hello` carries a version **range** (`min_version`..`version`); negotiation is symmetric and picks the highest overlap | Both sides reach the same answer without another round trip; old peers can be supported by lowering `MIN_PROTOCOL_VERSION` |
| 2026-10-11 | ALPN is the unversioned `kanodesk` | Versioning is `Hello`'s job; a versioned ALPN would fail the TLS handshake before a useful error can be sent |
| 2026-10-11 | `VideoFrame` carries `capture_us` and `host_delay_us` | Lets any viewer split latency into host and network parts; also input for QoS (16 §4 row 3.2) |
| 2026-10-11 | Input key codes are USB HID usages | Platform-neutral physical key ids for Map mode (07); each OS backend maps them to its scan codes |
| 2026-10-11 | Fuzz target body is library code (`kanodesk_proto::fuzz`) | Stable CI exercises it via proptest; `cargo fuzz` adds coverage-guided search and ASan |
| 2026-10-11 | ID server authenticates by signing the TLS channel binding (`ServerHello`), not by its TLS certificate | The pinned key is the server's ed25519 key (16 §5 item 2); binding the signature to the TLS session stops a MITM from replaying it, without certificate management |
| 2026-10-11 | Devices prove key ownership at registration by signing the channel binding + requested ID | Nobody can register (or take over) an ID for a key they do not hold, and a registration cannot be replayed on another connection |
| 2026-10-11 | One QUIC connection per device to the ID server, one bidi stream with request IDs, server pushes with `request_id = 0` | Simple request/reply plus pushes; the same UDP socket is the one hole punching will use next |
| 2026-10-11 | Server signs records on demand with a fresh `issued_at` | Cheap (ed25519), and lets clients reject stale records later if needed |
| 2026-10-11 | sqlx with `sqlite-bundled` only (no macros, no extension loading) | No `DATABASE_URL` needed at build time; a server should not load SQLite extensions |
| 2026-10-11 | Device IDs are random 9-digit numbers (100 000 000–999 999 999) | 900 M space, unguessable sequence; RustDesk uses 9-digit numeric IDs too |
| 2026-10-11 | Registered connections pay from a per-device budget, unregistered ones from the per-IP budget | Devices behind one NAT stop starving each other, while unauthenticated traffic is still bounded per IP; new IDs stay per IP to stop squatting |
| 2026-10-11 | Relay chosen by the ID server (round-robin over `--relay`), same value to both sides | Both peers must meet at one relay; the server is the only party both trust for that |
| 2026-10-11 | Key-loss recovery is an operator action (`remove`), not a protocol feature | A self-service "I lost my key" flow would let anyone steal an ID; the operator can check out of band |
| 2026-10-11 | Database lock file with `File::try_lock`; workspace `rust-version` raised from 1.85 to 1.89 | Prevents admin edits under a running server and two servers on one database; `try_lock` is std since 1.89 |
| 2026-10-11 | `FileKeyStore` for non-Windows hosts | Lets the ID server binary run on Linux servers now; DPAPI stays the Windows choice |
| 2026-10-11 | Online admin authenticated by the server's own signing key (signature over the TLS channel binding) | No extra secret to manage; possession of the server key already means full control, and the key store limits it to local administrators |
| 2026-10-11 | Admin uses the same rendezvous stream as devices, gated by `AdminAuth` per connection | One protocol and one listener; nothing extra to expose or firewall |
| 2026-10-11 | `ConfigUpdate` sent before the `RegisterResult` reply | Devices know the relays as soon as `register` returns, without waiting for a later push |
| 2026-10-11 | Relay list persisted in the database; `--relay` overrides | Runtime changes survive restarts without editing service command lines |
| 2026-10-11 | Relay session token (16 random bytes) issued by the ID server per connect request | The relay pairs the two sides by it (prompt 7); unguessable, so a third party cannot join a relayed session |
| 2026-10-11 | One dual-stack UDP socket per device for everything (ID server, peers, relay) | The address the ID server observes is exactly the NAT mapping peers must reach; IPv4 and IPv6 without a second socket |
| 2026-10-11 | Punch with raw datagrams from a cloned socket handle; quinn keeps receiving | quinn owns receives; send-only raw datagrams open NAT mappings and QUIC ignores them on arrival |
| 2026-10-11 | Relay is TURN-like and blind: forwards whole UDP datagrams (QUIC packets) per session | TLS + Noise stay end to end (16 §4 row 3.4); the relay needs no QUIC state or keys |
| 2026-10-11 | One relay data port per session; addresses learned from hello datagrams on that port | Several sessions to one host stay apart without parsing QUIC connection IDs; works behind symmetric NATs because the data path itself is used |
| 2026-10-11 | Relay sessions need an ID-server ticket (MAC with a shared secret, 120 s) | "Session issued by the idserver" without the relay calling the ID server; no open relay |
| 2026-10-11 | NAT test = second ID-server port, compared from one socket | Same idea as RustDesk's 21115/21116 test, over QUIC, no STUN dependency |
| 2026-10-11 | Private IPv4 addresses are shared only when both peers have the same public IP | Same-LAN shortcut without revealing LAN layouts to strangers; global IPv6 is public anyway |
| 2026-10-11 | Strategy: LAN (1.5 s) → direct IPv6 + IPv4 raced (5 s) → relay (10 s) | Prompt order; racing within a phase picks the fastest working address |
| 2026-10-11 | One ed25519 key per device, converted to X25519 for Noise | One identity for signatures (ID server) and key agreement (Noise); the conversion is the standard birational map |
| 2026-10-11 | Peers authenticate with Noise IK whose prologue carries the TLS channel binding | The host key comes from the ID server's signed record (or the user), not a certificate; binding ties Noise to this TLS session, so terminating TLS twice fails |
| 2026-10-11 | Password login is SPAKE2 with two slots (temporary, permanent); the client proves first, bound to the Noise handshake hash | The password never crosses the wire and offline guessing from a transcript is impossible; client-first confirmation means a wrong guess teaches the client nothing |
| 2026-10-11 | Permanent password stored DPAPI-protected on the host, not via OPAQUE | SPAKE2 needs the password on the host anyway; OPAQUE would add a dependency for little gain on a single-machine store |
| 2026-10-11 | Session layer lives in `kanodesk-transport` (`session.rs`) | Used by the spike, the CLI diagnostics and later the real host and client |
| 2026-10-11 | Spike host: a new viewer replaces the active one only after logging in | An unauthenticated connection must not be able to kick a viewer off |
| 2026-10-11 | A temporary password admits exactly one login: rotated at login, a generation counter refuses a concurrent second login (`PasswordUsed`); also rotated after repeated failures | Nobody else who saw the password can log in (or, in the spike, take over the viewer) during a session; 04 §7 |
| 2026-10-11 | Login throttle state saved to a text file in the host's data dir after every attempt, bans until `--reset-login-limits` | A restart (crash, update, reboot) must not hand an attacker fresh free attempts; plain text because it is not secret |
| 2026-10-11 | Hypervisor/container adapters left out of local addresses by name, unless they carry the primary route; VPN adapters kept | Their addresses only reach local VMs; name matching is crude but has no false positives on the real adapters seen so far |
| 2026-10-11 | Password prompts via `rpassword`, piped stdin still accepted | Hidden input on consoles, scriptable for tests |
| 2026-10-11 | Public IPv4 local addresses are shared with any peer, like global IPv6 | They are reachable from anywhere anyway; this is what makes UPnP mappings and directly connected hosts usable |
| 2026-10-11 | UPnP via `igd-next`, best effort, lease 1 h renewed every 30 min | Pure Rust, tokio support; many routers have UPnP off, so nothing depends on it |
| 2026-10-11 | Port prediction: next 16 ports above the observed one, only toward symmetric NATs | Cheap (a few extra punch datagrams), helps sequential allocators, harmless otherwise |
| 2026-10-11 | Keys travel as USB HID usages (Map mode); the Windows backend converts them to set-1 scan codes | Platform-neutral physical key ids (decided in prompt 4); scan codes make the host's layout decide the character, as Map mode requires |
| 2026-10-11 | Own `SendInput` backend instead of `enigo` | We need scan-code injection with the extended flag, absolute moves over the whole virtual desktop in physical pixels, and an extra-info marker; a thin wrapper over the `windows` crate we already use does exactly that |
| 2026-10-11 | Mouse positions are display-relative on the wire; the host adds the display's origin | The viewer never needs the host's virtual-desktop layout; displays left of or above the primary (negative origins) just work |
| 2026-10-11 | `SendInput` coordinates: n = ceil(offset × 65535 / (size − 1)) | Measured: the "÷ 65536" reading lands one pixel short mid-desktop; this lands on the exact pixel on both displays here |
| 2026-10-11 | Input on its own unidirectional QUIC stream, priority 20, ordered and reliable | Above video and control so input never waits behind them; order matters for input (a release must not overtake its press) |
| 2026-10-11 | Pointer moves coalesced to the latest one per 16.7 ms, flushed before any other event | 07 §6; keeps the stream small without reordering clicks and keys relative to moves |
| 2026-10-11 | Release everything on focus loss and close (viewer), on end of stream, permission loss, drop, and 3 s of silence while holding (host) | 07 §6; the keep-alive (an empty `InputMessage` every second while holding) brings a killed viewer's stuck keys down in seconds instead of at QUIC's 30 s idle timeout |
| 2026-10-11 | Injected events carry a marker in their extra info; the viewer ignores marked events | A host and viewer on one machine would otherwise feed each other's input in a loop |
| 2026-10-12 | Viewer grabs the keyboard with a low-level hook while in front (Map mode only), routing all keys through it | The only way to forward Win/Alt+Tab/Alt+F4; one key source keeps the order exact; lock keys and a local host's injections pass through |
| 2026-10-12 | Lock keys synchronised as states, not forwarded as keys | The viewer's lock LEDs keep meaning something; the host matches before any key that depends on them; no double toggles |
| 2026-10-12 | Non-keyboard-page keys as `(page << 16) | usage` in the existing `KeyEvent.code` | Media keys without a new message; keyboard-page values unchanged |
| 2026-10-12 | Media keys, Pause and Lang keys injected as virtual keys | Their scan codes vary between keyboards or cannot be expressed; the virtual keys are what Windows apps act on |
| 2026-10-12 | Pointer sent separately (shape once, then positions) rather than drawn into frames | No re-encoding for pointer moves; the controlling viewer shows the host's shape on its own pointer without network delay; view-only viewers draw it |
| 2026-10-12 | Translate mode: printable text without Ctrl/Alt/Win (AltGr allowed) as `TextInput`, everything else as keys | Shortcuts keep working on the host's layout while characters follow the viewer's layout |
| 2026-10-12 | Ctrl+Alt+Del and lock screen as an input action; Ctrl+Alt+Del deferred to the service | `SendSAS` needs LocalSystem (prompt 11); the wire action exists now so the UI can offer it |
| 2026-10-12 | Click approval = `AuthStart` without SPAKE2 messages; the host answers `LoginPending`, then `LoginResult` | No extra round trip or message for the request itself; a click-only host can still be reached by clients that send a password |
| 2026-10-12 | Login split into `host_authenticate` → `PendingLogin` → accept/reject | The engine decides (CM, policy) between proving who the viewer is and letting it in; nothing but control messages flows before |
